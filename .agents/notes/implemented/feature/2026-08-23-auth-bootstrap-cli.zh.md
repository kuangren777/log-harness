# Agent Note: The first administrator is created by a local CLI, not over the network

Status: implemented

[English](2026-08-23-auth-bootstrap-cli.md) | 中文

## Problem

[auth 能力](../architecture/2026-08-23-auth-capability-design.zh.md)把管理员权限定义为某个内置组的成员身份，而全新的 `auth.db` 中这个组没有任何成员。部署内部无法授予第一个成员身份：该 seam 提供的每一项管理操作都要求一个管理员 principal（主体），因此在有人成为管理员之前，新的多用户安装始终处于停滞状态。

常见做法——用首次运行的注册页面把管理员权限授予最先访问者——实际上是运维人员与互联网之间的一场竞赛。谁先加载该页面谁就拥有这套部署，而只要存储中还没有管理员，这个窗口就一直敞开。改为附带一个预置账号，则只是把问题转移成了一个已公开的密码。

## Decision

`dsh auth bootstrap --email <address>` 创建第一个管理员，且它只以启动器子命令的形式存在。它直接通过 `@deepseek-ai/dsh-auth-sqlite` 打开 `<harness home>/auth.db`：不启动任何 Cordis 应用，不挂载任何服务，也不生成任何 Typert 方法，因此不存在任何让网络对端触达它的代码路径。对 harness home 的写权限就是授权的替代物，而这正是区分运维人员与远程调用方的那项权限。另一条路是写一个必须正确的权限校验；而这里的做法是让这项操作根本不出现在需要校验的地方。

[`apps/cli/src/auth-cli.ts`](../../../../apps/cli/src/auth-cli.ts) 负责该动作，[`apps/cli/src/args.ts`](../../../../apps/cli/src/args.ts) 负责命令语法；`--home <path>` 通过共享的 `resolveDshHome` 覆盖 `$DSH_HOME`，使测试与运维人员以同样的方式指向同一个存储。

### 一旦存在管理员即拒绝

命令首先读取内置组的成员列表，若非空则以非零退出码拒绝——这发生在检查地址、密码或任何其他内容之前。正是这条不变量使该命令无法成为提权路径：它只可能在一个尚无任何可提权对象的部署上运行。它不是某个后续 flag 可以豁免的便利性检查——这里没有 `--force`，因为 `--force` 所对应的操作其实是「新增一名管理员」，而那已由需要认证的管理面负责。

### 密码来源及其优先级

只要 `DSH_BOOTSTRAP_PASSWORD` 有定义，它就优先；否则命令在终端上提示输入，并把 readline 的输出导向一个丢弃一切的 sink，因此输入内容不会回显，行内容也不会被重放。两个来源都没有时，命令拒绝执行并同时指出这两种方式，而不是从 argv 读取密码——那会让密码落入 shell 历史，并出现在该主机的每一次进程列表中。已定义但为空的变量会被采用，而不是当作未设置：空值意味着部署脚本出了问题，而回退到交互提示会把这个故障掩盖在一个看似正常工作的命令背后。最小长度固定为 12 个字符而非可配置项，因为最有可能把它调低的部署，恰恰是最承受不起短密码的那一个。

密码不会进入输出或存储。它在插入前由 `createUser` 完成哈希，任何拒绝消息都不引用它，长度拒绝也只陈述长度。

### 创建与提升

未知地址会创建账号、添加成员身份，并保持 `email_verified_at` 未设置，让首次登录负责验证。已存在账号的地址会被提升进该组，其密码保持不变，且这条路径根本不会读取密码。若改为拒绝，就会让那些账号以其他方式创建的部署陷入困境：它既没有管理员，也没有办法获得一个。而重写该账号的密码会把一条恢复命令变成账号劫持，因此提升只改变一件事——成员身份——并且成功输出行会说明密码未变更。

内置组由 provider 自身的 schema 物化，因此本命令从不创建它。当它缺失时，存储的 `unknown-subject` 拒绝会作为一次明确失败浮现，而不是用本命令临时造出的组敷衍过去——那样的组会带着错误的 id 和 `builtin=0`。

## Alternatives considered

**首次运行的 Web 注册页面。** 已否决，因为在运维人员完成配置之前部署就已可被访问，页面会把全部权限授予最先到达者。这场竞赛没有安全的时长。

**带已知密码的预置默认管理员。** 已否决，因为密码在发布的那一刻就已公开，而从不轮换它的安装等于交付了一个敞开的账号。

**首次启动时打印一次性 bootstrap token。** 已否决，因为它严格弱于它想取代的文件访问检查：token 必须被打印到某处、从某处读取、并以某种方式过期，而每一环都是新的泄漏途径。对 `auth.db` 的本地写权限本就是必要的，而且本就足够。

**在「尚无管理员」守卫之后提供一个 RPC 方法。** 已否决，因为该守卫就是这项操作的全部安全性，而它会位于一个专职接受匿名连接的面上。一项无法被触达的操作，其守卫也无从被绕过。

**用 `--password` flag 传入密码。** 已否决，因为 argv 对本机每个账号都可通过 `ps` 看到，并会写入 shell 历史。环境变量并没有好多少，但它是部署脚本所需的接口，而且是显式选用的。

**地址已存在时拒绝执行。** 已否决，因为那会让一个有账号却没有管理员的存储陷入困境，而这恰恰是本命令要修复的状态。

## Testing

[`apps/cli/tests/auth-cli.spec.ts`](../../../../apps/cli/tests/auth-cli.spec.ts) 针对临时 harness home 驱动该动作，并直接读取产生的 SQLite 文件：创建路径写入用户、成员身份和 `auth.bootstrap` 审计记录，且地址处于未验证状态；第二次运行以非零退出码拒绝，并使 `users`、`memberships` 和 `audit_log` 的转储逐字节保持不变；每种密码来源、缺少来源的拒绝、长度拒绝以及各种地址格式拒绝都是独立用例；另有一个用例扫描两条输出流和整个数据库以确认明文不存在。[`apps/cli/tests/args.spec.ts`](../../../../apps/cli/tests/args.spec.ts) 覆盖命令语法，包括 `auth` 与 `auth bootstrap` 保留各自的 `-h`，而根启动器把 `-h` 交给被启动的应用。

## Consequences

新的多用户部署只有一套 bootstrap 流程，它需要主机的 shell 访问权限，并且在部署的整个生命周期内都无法远程执行。丢失全部管理员账号的运维人员，可用同一条命令提升某个既有账号来恢复，无需重置密码。代价是：对于永远拿不到 shell 的托管控制台，bootstrap 不可用；而且 `dsh` 现在依赖 SQLite auth provider——启动器链接了它此前没有理由知晓的那个存储。
