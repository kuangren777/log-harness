# Agent Note: 手机上的客户端，以及从某个 origin 装下来的那个应用

Status: implemented

[English](2026-08-23-mobile-web-and-pwa.md) | 中文

## 问题

Web 客户端是为宽屏上的光标画的。在 390x844 下，三栏框架只把 56px 侧边栏控制栏剩下的空间留给会话；设置对话框仍保留 188px 导航栏，而旁边的内容列窄到放不下一行设置项；控件停留在 28–36px 的光标尺寸；控制栏的展开操作靠 hover 才出现——而手指永远做不出 hover；`height: 100%` 相对大视口解析，因此输入区一出生就落在浏览器界面之下。当时既没有 service worker，manifest 也只是带一个 SVG 图标的四行残桩，所以那台 tailnet 部署根本装不到主屏幕上。

## 决策

### 一个断点，断点之上什么都不变

`PHONE_MAX_WIDTH = 640`（ui-layout `columns.ts`）。在它及以下，AppFrame 是彻底离开三栏形态，而不是把它压小：一栏占满宽度的会话轨道，其上是承载抽屉开关的横条，详情栏移出文档流，侧边栏则以宽形态渲染在离屏抽屉中。640 高于两个手机目标宽度、低于最窄的平板竖屏宽度，因此既有的 1024px 控制栏自动折叠与全部宽形态规则都原封不动。其他包里的 CSS Module 会重复这个字面量，因为自定义属性无法在媒体查询中读取；常量是权威，每处重复都点名它。

### 抽屉就是侧边栏原有的那个开关，不是第二个

在 1024 以下，布局 store 已经有 `narrowExpanded`——把自动折叠的侧边栏重新展开的手动覆盖标志。抽屉就是这个标志。于是横条开关、侧边栏自带的折叠控件与 `ctx.layout.toggleSidebar()` 仍是同一个开关，不可能自相矛盾，也没有新增需要同步的 store 状态。

模态是真的：Escape、点击遮罩和开关都会关闭它，Tab 在其内部循环（`drawer.ts` 收纳了那两个纯决策），进入时落在第一个控件上，关闭时焦点回到打开它的那个控件——除非焦点早已离开抽屉，那种情况下抢回焦点才是无礼的。停放中的抽屉靠 `visibility: hidden` 移出 tab 顺序，切换时机分别在滑出的末尾与滑入的开头，因此两个方向都不会遮住动画；只用 transform 会留下一整列看不见却仍可 Tab 到的控件。

### 抽屉用 `left` 滑动，不用 transform

带 transform 的祖先会成为 `position: fixed` 后代的包含块。ui-settings 把它的全视口面板渲染为侧边栏列的后代，因此当抽屉带 `transform: translateX(0)` 时，设置对话框宽度变成了 280px 而不是 390——手机 journey 抓到的正是这一点。AppFrame 本就以 px 求解抽屉宽度，于是由它内联给出宽度以及停放／打开时的 `left`，过渡就走这个属性。

### 用 dvh，因为键盘也是视口的一部分

`html`、`body` 与 `#root` 在 `@supports` 守卫下改为 `100dvh`，百分比作为回退。百分比是相对*大*视口解析的——地址栏收起时的那个——因此框架的底部一行，也就是输入区，一开始就落在浏览器界面之下，直到用户滚动才露出来。动态单位会随着这些界面和屏幕键盘的移动跟踪可见视口。备选是 `svh`：稳定、永不重排，也永远短了一个地址栏的高度，那片空缺会露出应用下方的页面背景。`dvh` 会在界面移动时重排，这就是付出的代价。

安全区内边距只应用一次，在框架、它的横条、抽屉和中间列上——只有这些盒子接触屏幕边缘——而文档里的 `viewport-fit=cover` 才是让这些内边距解析出非零值的前提。

### 点按目标是指针问题，不是宽度问题

44px 应用在 `@media (pointer: coarse)` 下，它对以触摸为主的设备为真，对由鼠标驱动的触屏笔记本为假。它覆盖共享 `Button` 的默认尺寸与 `Input`、输入区的附件／发送圆钮与模式胶囊、侧边栏的宽形态控件，以及设置的关闭按钮与导航单元。紧凑的 `sm` 按钮与 56px 控制栏里的 36px 方块刻意保持原尺寸：44px 控件放不进 56px 的列，而把为密集行设计的控件撑大只会撑坏行，帮不到手指。在 `(hover: none)` 下，控制栏那个靠 hover 显示的展开图标变为始终显示，因为那里等不到 hover。

### `/api` 永不缓存，worker 永不等待

`public/sw.js` 是手写并从 `public/` 原样发布的，因此其 URL 在各次部署间稳定为 `/sw.js`，浏览器的逐字节比较才能识别出更新。它在安装时预缓存文档、manifest 与图标，并在带哈希的构建产物首次被请求时缓存它们——带哈希的名字不会陈旧，因为新构建请求的是新 URL。

它拒绝处理 `/api` 之下的每一个请求，该前缀承载全部 RPC 调用与两条事件 WebSocket 下行。那里的缓存应答会报告一个 Host 已不再持有的会话、审批或权限状态；离线时正确的答案是报错，而不是一个自信的错误答案。

更新策略是**`skipWaiting` 加 `clients.claim`，且不强制重载**。立即接管才能阻止一个已重新部署的 origin 在所有标签页关闭前一直被喂旧外壳。重载是刻意不做的：导航请求优先走网络，在线页面本就能拿到刚部署的文档，缓存永远只是离线回退——在线时外壳不可能陈旧，而 `controllerchange` 重载只会赔上正在进行的一轮对话的界面状态。下一次导航自然会取到新外壳。

只在 `https:` 或回环主机名下注册，因为浏览器只在那里暴露 `navigator.serviceWorker`。部署在明文 http 的局域网地址上时只能在线运行、没有安装提示；这是浏览器的规则，这里如实记录而非绕开。

### PWA 属于一个 origin——这是约束，不是要绕开的缺陷

已安装的应用绑定在安装时的那个 origin 上，而本部署的会话 cookie 是 `SameSite=Strict`。因此从服务器 A 安装的应用无法向服务器 B 认证：cookie 不会被发送，况且已安装的 scope 本来也覆盖不到 B。这里没有加跨 origin 的"服务器地址"输入项，因为这样的输入项不可能生效。

受支持的形态恰好相反：每个 dsh 部署各自提供一份可安装的应用，各自为自己的 origin 保管自己的 cookie。将来的"最近使用过的 origin"列表只会*导航*过去，绝不代理它们。这一点写在 `apps/web/README.zh.md` 里，因为要找那个设置项的人会去那里找。

## 考虑过的替代方案

**在会话标题栏上浮一个开关。** 否决：会话标题栏在 hero 阶段是隐藏的，控件恰好会在新用户第一次需要侧边栏时消失。44px 的横条要占竖向空间，但它始终存在。

**用 Vite 构建 service worker。** 否决：service worker 的文件名不能带哈希，而 module worker 至今仍不普及。第二个 rollup 入口还会让共享 chunk 从一个无法 import 它们的 worker 里被拆出去。

**做一个显式的更新提示。** 暂时否决：它需要产品文案和某个包里的界面，而导航优先走网络已经让在线的陈旧外壳不可能出现。策略记录在此，以便日后要加提示时，替换的是一个有据可依的选择，而不是一次意外。

**仅按宽度把所有控件撑到 44px。** 否决：由鼠标驱动的窄桌面窗口不需要手指大小的控件，而 `(pointer: coarse)` 说的正是真正的条件。

## 后果

桌面端逐字节不变：每一条新规则都在 `max-width: 640px`、`pointer: coarse`、`hover: none`，或框架只在断点以下设置的 `data-phone` 属性之后。没有既有 golden 发生位移。

手机上仍未解决的部分：iOS Safari 不会为屏幕键盘调整布局视口，因此 `dvh` 在那里不会收缩，输入区依赖 Safari 把获得焦点的 textarea 滚动进视野——Android 上的 Chrome 会调整，表现符合设计。设置对话框的手机形态是把关闭按钮叠在导航条之上，而不是重排页头；各分区主体本身也没有重新布局，过宽的设置行仍在自己的容器内滚动。`ui-workspace` 的会话行保留原有的 hover 操作——那个包不在本次改动范围内。
