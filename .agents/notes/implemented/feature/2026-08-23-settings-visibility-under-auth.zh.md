# Agent Note：被拒绝的设置分区应当不存在，而不是坏掉

Status: implemented

[English](2026-08-23-settings-visibility-under-auth.md) | 中文

## 问题

挂载认证之后，配置平面是管理员专属的：`settings.describe`、各个设置写入方法、`credentials.*`、`skill.inventory`、`llm.discoverModels`，以及 agent preset 的编写方法，全都是 `admin` 行。浏览器并不知道这件事。非管理员打开设置，导航里照样列着 General、Models、Skills、Plugins 和 Agent presets，点进去正文渲染的是原始 `HTTP 403` 加一个 Retry 按钮 —— 把传输层自己的措辞当成产品状态呈现，还配了一个永远不会成功的控件。

与管理 RPC 一同写出的 Access 分区，本来就会降级为一段有解释的空状态。正是这种不对称让缺陷变得刺眼：一个分区知道答案，其余几个在猜。

## 决定

### mirror 报告的是可达性，不只是失败

`SettingsMirrorSnapshot` 在 `status` 与 `error` 之外新增 `reach: 'unknown' | 'granted' | 'refused'`。拒绝是一个重试也不会改变的决定，传输故障则是会恢复的抖动。把两者压成同一个 `error` 字符串，正是「给一个 Host 早已裁定的答案配上 Retry 按钮」的成因。现在每个派生界面读的是 Host 自己的答复，而不是去模式匹配一段错误文案。

### 调用者用不了的分区，根本不注册

那些整体依赖被拒平面的分区 —— Models 及其两个 onboarding 步骤、Plugins、Skills —— 在 reach 为 `refused` 时完全不注册。在这里，隐藏入口才是诚实的形态：页面既无内容可展示，也无操作可提供，空状态只会变成一行专门用来道歉的条目。composer 的模型选择器不受影响：它读的是 Host 仍然提供的目录 `llm.models`（`user` 行），且位于另一个包中。

### 客户端不是权威

隐藏一个分区并不授予任何东西。对同一个调用者，这些方法在 Host 上一律被拒，表驱动的策略巡检对每一条 `admin` 行都证明了这点。即便把这段代码删掉，非管理员会重新看到这些分区，而其中每一次调用仍然失败 —— 这正是「拒绝」与「呈现」之间应有的关系。

## 考虑过的替代方案

**每个分区都渲染成有解释的空状态。** 对完全属于管理员的分区否决：连续五行道歉比一份更短的列表更糟。Access 分区保留空状态，因为管理员本就会去找它，需要知道为什么它不属于自己。

**在每个分区内部匹配 403 状态码。** 否决 —— 那会把一个传输层细节塞进五个包，并且在有人新增第六个时必然遗漏。

## 后果

非管理员的设置对话框变短，且说的是实话。未挂载认证的部署毫无变化：reach 恒为 `granted`，每个分区照旧注册。日后新增的分区需要自行决定行为，而 reach 字段就是它据以决定的依据。
