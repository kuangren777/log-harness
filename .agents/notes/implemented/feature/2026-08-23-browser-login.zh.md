# Agent Note: 浏览器从 401 得知需要登录，除此之外不做任何判断

Status: implemented

[English](2026-08-23-browser-login.md) | 中文

## Problem

[请求门](2026-08-23-auth-bootstrap-cli.zh.md)让 `dsh web` 部署具备了拒绝能力：未认证的 `/api` 请求得到 401，WebSocket 升级同样被拒。浏览器里没有任何东西知道该拿它怎么办。外壳看到的是一次传输失败，于是进入重连循环，反复重试一个永远会被同样拒绝的请求，结果一个会认证的部署表现得像一个坏掉的部署。

解决它的界面要同时满足两个互相拉扯的约束。它必须存在于已发布的 Web 组合里，因为部署是通过 `--patch` overlay 选择启用认证的，而 overlay 只能追加 host 行，无法往已经构建好的 bundle 里追加浏览器行。同时它在单租户默认部署——也就是所有没有叠加该 overlay 的部署——中必须完全不可见。

## Decision

`@deepseek-ai/dsh-client-ui-auth` 是 Web bundle 的一个已发布行。它在一个控制器之上注册两个座位——`shell.overlay` 中的登录卡片与 `sidebar.footer.action` 中的账号行——而控制器做的第一件事，是在门的 `/auth` 通道上调用 `me`。

让默认部署保持安静的，是"不存在"本身。`/auth` 是门注册的通道；没有门就没有这条路由，调用在传输层失败，控制器记下 `mounted: false`，两个座位在这一页的余生里都保持隐藏。没有任何配置项来选择这一点，也不需要与 overlay 同步添加 host 行：同一个 bundle 表现出两种行为，因为它提出的那个问题本就有两个诚实的答案。

### 401 接缝是一个传输层不去处理的锁存量

`WebApiClient.doFetch` 观察 `response.status === 401` 并调用一个可选回调；应答照旧返回给调用方，仍然是一直以来的那次传输失败。插件体把这个回调变成 `ctx.connection.authRequired`——一个与既有 `hostDescription` 并列的裸可观察源，而 `ui-auth` 是它唯一的读者。

这个信号会自锁——只有一次 false 到 true 的转变，永不清除。拒绝过一次的部署会拒绝之后的每一次调用，而能改变答案的那份凭据，是通过登录界面重载的页面到来的，所以没有可以回退的状态。保持它单调，也就免去了消费者本来必须做对的那条重置路径。

翻转时，界面并不直接打开表单，而是调用 `me`。这次拒绝可能与另一个标签页中已经成功的登录相竞争，而只有 Host 知道真相。

### 界面不对授权做任何判断

卡片可见时，Host 早已完成拒绝。界面显示的一切都是门给出的答案——cookie 是否认证到人、密码是否开启了一次挑战、验证码是否兑换、令牌是否仍然有效。这里没有客户端的权限检查、没有权利模型、也没有被藏起来的控件：已登录账号不可执行的操作由网关的策略表拒绝，而不是由一个决定不渲染按钮的组件拒绝。

这也正是登录与退出都重载页面的原因。给一条活着的连接重新认证，意味着在流已经以旧凭据打开的情况下，重新驱动外壳连接后的整套流程——那是浏览器本就能正确完成的那次启动的第二个、更弱的版本。

### 笼统的失败文案是契约的一部分，而不是措辞偏好

门对密码错误、地址未知、账号停用、验证码过期，一律回答同一个没有形状的 `failed`，正是为了让登录表单无法枚举账号。写成"该地址没有账号"的文案会在客户端重建服务端拒绝充当的那个预言机，而客户端恰恰是没人会想到去查的地方。

因此一句话覆盖上述全部情形，重设请求的回执写成"如果该地址有账号"，速率限制的拒绝读作"请稍后再试"，不给出次数、期限或尝试总数——Host 报告的期限只用于选择措辞，从不被渲染。单元测试固定了这一点：两种拒绝原因必须产生完全相同的提示，且这些字符串会被对照那些会泄露差别的表述做检查。

### fixture 支持是选择性启用的

fixture 客户端只在 `?fixtureAuth=on` 下服务 `/auth`。fixture 页面就是一个没有请求门的部署，而现有的每一条 fixture 旅程都断言外壳前面没有登录卡片；默认服务这个通道就会在那里放上一张。

## Consequences

`ConnectionHandle`多了一个成员，因此客户端测试里每一个手工搭建的替身现在都要提供 `authRequired` 源；`packages/client/runtime/tests` 中的两处已随本次改动一并更新。

没有请求门的部署在启动时多付出一样东西：一次发往 `/auth/me` 的失败 POST，它的拒绝就是答案。这是每次页面加载一个请求，也正是让两种部署形态共用一个 bundle 的代价。

登录界面拥有两个邮件链接路径（`/reset-password`、`/verify-email`）。它们在本包内部与 `location.pathname` 比对，而不是走路由，因为外壳没有路由器；将来若引入路由器，必须把这两个路径一并接过去。

这里不涉及任何管理功能。创建账号、管理用户组、编辑规则都留在浏览器之外，账号行也刻意只展示 `me` 关于已登录账号所报告的内容。

## Alternatives considered

**从传输错误消息里解析 "HTTP 401"。** 否决：状态码是结构化信息，就在那个已经持有 `Response` 的地方可用，而从字符串里再读回来会把登录界面耦合到三层之外抛出的错误的措辞上。

**在 API 客户端内部把 401 翻译成一个已解决的"未认证"结果。** 否决，因为它改变了每一个既有调用方看到的东西。被拒绝的调用就是失败的调用；登录界面需要知道它，而其他调用方都不该被迫学习一种新的成功形态。

**把认证行做成由 overlay 追加的浏览器行。** 否决：`dsh.client` 行会被扫描进启动清单并由构建好的 bundle 提供，因此 `--patch` overlay 追加一行就要求该包在部署处已构建且可解析，而已发布的 bundle 仍然必须容忍它缺席。始终发布、默认隐藏，是一种行为而不是两种。

**登录成功后清除 `authRequired`。** 否决为不可达状态：成功路径会重载页面，把这个标志连同其他一切一并丢弃。清除路径存在的唯一意义将是无人测试。

**把账号行放进设置而不是侧边栏底部。** 否决，因为退出登录不是配置，而需要离开一台共用机器的人不应该先打开一个模态框。

**用一个"会话已过期"的 toast 取代卡片。** 否决：它背后的应用连一个请求都服务不了，一个可关闭的提示会把用户留在一个所有操作都静默失败的外壳里。
