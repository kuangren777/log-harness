# Agent Note: 邮件能力 seam——一个 send、两个提供方、凭据按引用传递

Status: implemented

[English](2026-08-23-mail-capability-seam.md) | 中文

## Problem

有若干产品路径需要 harness 向真人发出一封邮件：登录验证码、确认敏感操作的一次性验证码、运维通知。它们需要的是同样三件东西，而其中任何一件都不该由它们各自持有——一条会说 SMTP 的传输通道、一个永不出现在组合文件里的 SMTP 密码，以及一条让测试或浏览器旅程无需邮件服务器就能读回已发内容的路径。若按功能各写一份，每个功能都会带上自己的 nodemailer 接线、自己的密钥处理与自己的测试替身，而第二个功能只能靠猜是否与第一个一致。

## Decision

**一个[能力 seam](../../../../docs/glossary.zh.md#capability-seam)，三种角色分置三个包。** `@deepseek-ai/dsh-mail` 是 Service Definition：`ctx.mail` 上的抽象 `MailService`，只有一个操作 `send(message: MailMessage): Promise<void>`，作用于由 `to`、`subject`、`text` 与可选 `html` 组成的记录。`@deepseek-ai/dsh-mail-smtp` 与 `@deepseek-ai/dsh-mail-file` 是 Service Provider。Consumer 角色目前为空：没有任何组合挂载邮件提供方，因此本次不改动任何组合、快照或随产品发布的预设。

**本 seam 不持有地址语法。** `to` 按调用方书写的原样送达提供方。`MailMessage` 是同进程的类型化接口，调用方交不出非字符串；而判定地址能否投递的是传输通道——SMTP 服务器的 `RCPT TO`，或测试读回的那个文件。在这里放一个正则只会与它产生分歧。`from` 是提供方配置而非邮件字段，因此一个挂载的提供方以一个身份发信，消费方无法组装出另一个发件人。

**模板留给消费方。** 主题、正文、语言选择与收件人查找属于决定发什么的那个功能；本 seam 搬运的是已完成的内容，因此模板改动永远不会触及传输通道。

**凭据引用，而非密钥。** SMTP 提供方的 `userRef` 与 `passwordRef` 是凭据引用的**名字**，在加载时经 `credentialRef` 加品牌标记。两者在每一次发送时都经 `ctx.credentials` 解析，这正是轮换后的密码无需重启就能作用于下一封邮件的原因；解析出的值只存在于内存，所有诊断信息都指名引用而非其值。引用解析不到值、以及配置了引用却没有挂载凭据服务，两者都会明确报错并指名该引用。不符合凭据语法的引用，以及只配置两个引用之一的半截登录，失败得更早——在加载时，此时正在被读取的恰是携带该错误的组合文件。

**一个已解析登录对应一个传输通道。** 因为解析是每次发送进行的，传输通道复用以解析出的登录信息为键：登录未变则复用已开的 nodemailer 连接池，发生轮换则先关闭旧传输通道再打开新的，因此被撤回的密码绝不会继续维持一条已认证的活连接。`ctx.effect` 把活跃传输通道绑定到所属 fiber；释放资源时关闭它并拒绝之后的发送，第二次释放则无事可做。

**mail-file 的行格式是一项测试约定。** 每封受理的邮件追加一个紧凑 JSON 对象加 `\n`：`ts`（ISO-8601 UTC 受理时刻）、`to`、`subject`、`text`，以及仅当邮件携带时才出现的 `html`。单元测试套件、无密钥快照与浏览器旅程解析这些行来读回 harness 发出的内容——从登录邮件中取回 2FA 验证码是最初的动机——因此字段集合只随其消费方一起变化。信箱在创建时是 `0600`，重新打开上一次运行留下的可读文件时同样施加 `0600`，因为投递的邮件可能携带登录链接；这是安全不变量，不是部署选择。写入经由同一个队列串行化，因此行顺序即受理顺序，释放资源时会先等待已受理的写入结算，再关闭句柄。

## 为什么用 nodemailer

SMTP 帧、STARTTLS 协商、AUTH 机制选择、`text`／`html` 替代正文的 MIME 组装以及首部编码，是本仓库否则就要完全自持的一整套协议实现，还要连同让它对真实服务器保持正确的测试一起维护。nodemailer 有人维护、采用 MIT-0 许可、且未声明任何运行时依赖，因此引入它不增加传递性供应链面（[依赖策略](../process/2026-07-26-dependencies-over-hand-rolling.zh.md)）。提供方只依赖它的两个操作——`sendMail` 与 `close`——在本地声明为 `MailTransport`；正是这份窄声明让包内套件能对着一个记录型替身跑通每条路径而无需服务器，同时 `createSmtpTransport` 仍是导出的生产工厂与构造函数默认值。

## Testing

包内套件对全部六个源文件达成逐文件 100% 覆盖率。mail-file 固定了 JSON 行格式、向已有信箱追加、并发发送下的受理顺序、创建与重新打开两种情况下的 `0600`、父目录创建、路径无法打开时的拒绝，以及资源释放（已受理的写入被冲刷、之后的发送被拒绝、第二次释放无副作用）。mail-smtp 固定了加载期的引用加标与两类配置拒绝、认证与未认证中继下的传输通道参数、复用与轮换、两类明确的凭据失败、资源释放，以及一个日志 exporter 断言：任何记录中都不出现解析后的用户名或密码。`tests/mail-smtp.e2e.ts` 通过真实服务器投递，在 `DSH_SMTP_TEST_HOST`、`_PORT`、`_USER`、`_PASSWORD` 未全部设置时整体自跳过。

没有快照变化：既无 Consumer，模型与产品用户所见之物就没有任何移动。

## Alternatives considered

**用一个包承担三种角色。** 本 seam 第一天就有两个提供方，且它们因互不相关的原因演化——SMTP 的旋钮与信箱格式之间没有共同的发布压力——这正是[能力 seam 论证](2026-06-13-capability-seams.zh.md)要求拆分的情形。单包还会迫使 Service Definition 的每一个消费方都带上 nodemailer。

**直接写 `user` 与 `password` 配置字段。** 那会把密钥放进组合文件，而这正是凭据 seam 要防止的；并且值在加载时冻结，轮换就需要重启。

**启动时解析一次凭据。** 那样可以让一个传输通道服务整个进程生命周期、代码也略简单，代价却是凭据 seam 存在的那条性质：变更后的凭据要能作用于下一次操作。每次发送解析保住了这条性质，而在没有变化时只多付一次比较。

**自己实现 SMTP。** 按依赖策略陈述的同样理由否决：那会给一个以 agent（智能体）编排为主题的仓库塞进一套协议实现及其真实服务器测试负担。

**为可测试性加一个 `transportFactory` 配置字段。** 只有测试会设置的旋钮不是可配置性，而且它会允许组合文件指名任意工厂。工厂改为构造函数的第三个参数——`cordis.yml` 触及不到，默认为 `createSmtpTransport`，由直接构造提供方的套件传入。

**在 seam 中校验收件地址。** 依同进程信任规则否决：静态接口已经保证是字符串，而判定可投递性的边界是传输通道。第二套语法会拒绝服务器接受的地址，也会接受服务器不接受的地址。

**把 mail-file 写成每封邮件一次 `appendFile`。** 每次发送重新打开无法在不额外 stat 的情况下恢复既有信箱的属主专属权限，在并发发送下不提供顺序保证，也没给资源释放留下可以停稳的对象。

## Consequences

harness 获得了一个没有消费方的邮件能力，这是刻意为之：seam 与两个提供方都已完整且有测试，第一个需要邮件的功能自行组装邮件、挑选提供方，无需触及传输通道。因为没有任何挂载，这次新增对运行中的组合的代价为零。

`nodemailer` 只为 `dsh-mail-smtp` 进入依赖图，`THIRD_PARTY_NOTICES.md` 记录了它。mail-file 的行格式如今是两类未来读者依赖的约定；改动它意味着同时改动读取信箱的套件与旅程，这是"只有一种可读格式"而非"每个测试一个替身"所要付的价钱。
