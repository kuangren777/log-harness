# @deepseek-ai/dsh-client-ui-layout

English | [中文](README.zh.md)

Shell plugin: the AppFrame shell (the sidebar drag handle and the column solver) plus the `ctx.layout` panel-geometry service; it registers into the runtime-owned `root` slot and declares `rail`, `sidebar`, `conversation`, `details`, `view`, and `shell.overlay`. The sidebar resize boundary is an invisible hit strip; the details column has no resize boundary at all — open, it takes `DETAILS_RATIO` (half) of the frame's inner width, and it auto-closes only when that share would squeeze the center below `DETAILS_CENTER_FLOOR`. A closed sidebar retains a 56px control rail while details closes to zero width. The package also seats the theme presenter: it consumes resolved `ctx.theme` snapshots and projects them onto the document (`html { color-scheme }` for native UA chrome, `body[data-ds-dark-theme]` from the active color scheme, the theme's alias tokens as inline variables on body, and one owned `<meta name="theme-color">` whose content follows the computed body background). Measuring after palette and token application keeps the rendered background as the single color authority; disposing the presenter removes its metadata node with its other global writes.

AppFrame always mounts the conversation and details columns; a connected Session renders through `SessionProvider`. The transient layout store starts the sidebar at its default width and details closed, and it never reads or writes `localStorage`. Hero and other unselected states also derive a zero rendered details width without changing that stored preference. AppFrame retains the last non-blank Session id across those states: the first Session remains closed, an explicit details action opens the contract default width, returning to the same Session restores its unchanged width, and selecting a different Session closes details before paint. The conversation owner share is empty, while the sidebar owner share contains only `collapsed` and `width`; registrants obtain business data from standard hooks and actions from their own inject faces.

The component root is a flex row: the `rail` column, then the grid frame. `rail` is an icon column left of the sidebar, and it sits BESIDE the grid rather than in it — the frame keeps exactly three tracks (external readers index them by position), and the box the frame's own ResizeObserver reports is already net of the rail, so no width is measured or subtracted anywhere. An unoccupied rail is a zero-width flex item and the three columns behave exactly as they did without it. Its occupant receives `{ view, showView }` and owns whatever inner seats it declares. `view` is a keyed slot of full-bleed top-level surfaces: while the frame's view is anything other than `CONVERSATION_VIEW`, the entry registered under that id renders in an extra grid cell spanning all three tracks, and the sidebar and details tracks collapse to zero. The three column occupants are NOT unmounted — they stay in place and keep rendering behind the view, marked `data-view-hidden` with `aria-hidden` and `inert` and hidden through `visibility` rather than `display`, so an in-progress composer draft, a scroll offset, and every other piece of DOM-held state survives a view round trip intact. The details column's width is a product decision, not a preference: there is no drag handle and no wide mode for it, and the frame publishes `data-view` for CSS.

`ctx.layout` also carries the details column's mode gesture, so a plugin contributing one mode can raise its own body without importing the plugin that owns the column: `showDetailsMode(id)` selects the `conversation.details.mode` entry named by `id` and then opens the column. The write itself belongs to the occupant, which registers a selector through `registerDetailsModeSelector` and disposes it with its fiber; the latest registration replaces the previous one, and a superseded disposer removes nothing, so an HMR swap keeps the fresh selector. Selection precedes the open, so the column never paints the previous mode first. With no registered selector nothing is written and the gesture is exactly `openDetails`; an id naming no live entry leaves the panel on `tool`. `showView(id)` switches the frame's top-level view (`CONVERSATION_VIEW` restores the three columns).

The `/client` exports are the plugin body (`apply`/`inject`), `LayoutController`, the `CONVERSATION_VIEW` id, and the six owner-share interfaces. AppFrame, the panel store, and the column solver remain package-internal.

## Model Experience

None, as the layout shell manages browser viewing state; nothing here reaches a model request.

#### KV Cache effect

None; this package neither assembles nor sends a provider request.

## Known Limitations and Deferred Work

- **Panel geometry is transient** — reload restores the sidebar default and details closed; switching between distinct Session ids also closes details, while unselected surfaces render details at zero width without modifying geometry.
- **Auto-close derives a zero width without touching the open preference** — the column restores itself when the window widens; consumers must not read the stored details value as the rendered truth (the solver owns the rendered width).
- **Parked columns still render** — a keyed view hides the three columns rather than unmounting them (which is what preserves their state), so a heavy conversation keeps paying its render cost behind the view; a view that needs the frame to itself must still expect the columns to be live in the tree.
- **No scroll anchoring during squeeze reflow** — layout changes may move the reader's viewport.
