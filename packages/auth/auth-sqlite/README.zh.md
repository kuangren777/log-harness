# dsh-auth-sqlite

[English](README.md) | 中文

[认证与授权](../README.zh.md) seam 的 Service Provider：在单个 `node:sqlite` 数据库上实现 [`AuthService`](../auth/README.zh.md)，保存用户、组、规则、在用 auth session、一次性凭据、资源归属、限流窗口与审计日志。

## 存储

数据库位于配置的 `path`（出厂组合中为 `$DSH_HOME/auth.db`），以 WAL 优先方式打开，文件权限 `0600`。`AUTH_SCHEMA_VERSION` 写入 `PRAGMA user_version`，且**只拒绝、不迁移**：来自其他构建的数据库会在加载时报出两个版本号并失败，因此降级不可能悄悄地以错误方式解释凭据记录。

| `Config` 字段 | 含义 |
|---|---|
| `path` | 数据库文件；`:memory:` 给测试一个进程内存储。 |
| `journalMode` | `wal`（默认）、`delete`、`truncate` 或 `persist`。 |
| `sessionTtlMs` | 已签发 auth session 的绝对生存期；默认 30 天。 |

## 存储自身强制的约束

**通用登录失败。** 无论邮箱不存在、密码错误还是账号被禁用，`verifyLogin` 都返回同一种拒绝，因此无法借助响应枚举账号。

**持久化限流。** 密码、2FA 发送与重置尝试记录在 `rate_events` 的滑动窗口中，因此锁定会跨 Host 重启存活，而不是随进程一起清零。这些限额是安全不变量，不是部署旋钮。

**一次性凭据。** 一次性令牌在同一个事务中既写入 `consumed_at` 又返回用户，因此两个并发兑换不可能同时成功。兑换 `verify-email` 令牌会在同一个事务里写入 `users.email_verified_at`——花掉链接与记录它所证明的事实是同一件事，若拆成两次写入，中间崩溃就会让账户既未验证、又不再有可用于证明的凭据。2FA 验证码在尝试次数上限后额外作废。

**只存摘要。** auth session 令牌与一次性验证码以摘要存储、按摘要查找，再以 `timingSafeEqual` 确认。数据库与审计日志都不会持有明文密码、令牌或验证码。

**不可删除的 admin 组。** 内置组拒绝删除，因此部署不可能把所有管理员挡在自己的权限界面之外。

## 归属

`session_owners` 与 `workspace_owners` 把 agent 会话或工作区映射到创建它的用户。归属信息放在这里而不是会话日志中，因此为部署加上认证不会改变 `SESSION_FORMAT_VERSION` 或持久会话记录。

## 模型体验

无。该提供方服务于 Host 的授权决策：任何存储记录都不会进入模型请求，本包也不注册工具、prompt 分区或会话事件。

#### KV Cache 影响

无；本包不贡献任何请求内容，因此不会使任何前缀失效。

## 已知限制与后续工作

- **单进程存储** —— 一个启用 WAL 的 SQLite 文件服务一个 Host。第二个 Host 进程访问同一文件未经测试且不受支持；共享部署需要同一 seam 背后的另一种提供方。
- **只拒绝不迁移** —— schema 升版要求运维重建数据库，丢失用户与审计历史。第一个必须跨升级存活的版本会带来迁移路径。
- **审计不设保留上限** —— `audit_log` 不做裁剪地增长；在提供方内建策略之前，长期运行的部署需要自备保留策略。
