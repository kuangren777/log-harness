# dsh-mail-file

[English](README.md) | 中文

基于文件的[邮件](../mail/README.zh.md)提供方：每封投递的邮件都成为追加到指定信箱文件中的一行 JSON。单元测试套件、无密钥快照与浏览器旅程挂载它，用来读回 harness 发出的内容——从登录邮件中取回一次性验证码正是它存在的场景。

## 配置

| 字段 | 默认值 | 含义 |
|---|---|---|
| `path` | 必填 | 信箱文件。相对路径相对进程工作目录解析，缺失的父目录会被创建。 |

## 信箱行格式

每行一个紧凑 JSON 对象，以 `\n` 结尾。该格式是一项约定：消费方要解析它，因此下列字段只随消费方一起变化。

| 字段 | 含义 |
|---|---|
| `ts` | 提供方受理该邮件的 ISO-8601 UTC 时刻。 |
| `to` | 收件地址，原样取自 `MailMessage.to`。 |
| `subject` | 主题行，原样。 |
| `text` | 纯文本正文，原样。 |
| `html` | HTML 正文；仅当邮件携带它时该键才出现。 |

```jsonl
{"ts":"2026-08-23T09:41:07.412Z","to":"recipient@example.com","subject":"Your sign-in code","text":"Your code is 314159."}
{"ts":"2026-08-23T09:42:11.008Z","to":"recipient@example.com","subject":"Welcome","text":"Hello.","html":"<p>Hello.</p>"}
```

除此之外不会写出任何键，已有的行也永不重写，因此读取方可以逐行解析文件，并按到达顺序索引邮件。

## 文件处理

信箱以追加模式打开一次，并在提供方的生命周期内保持打开；发送经由同一个队列串行化，因此即便消费方并发发送，行顺序也是提供方受理邮件的顺序。

文件权限为 `0600`。投递的邮件可能携带登录链接或一次性验证码，因此无论是本提供方创建该文件，还是打开上一次运行留下的、对同组或所有人可读的信箱，都会施加该权限。这是安全不变量，不是部署选择，也没有任何配置字段能放宽它。

释放资源时会先等待已受理的写入结算，再关闭句柄。拆除前发出的发送仍会写入文件；拆除后发出的发送会被指名拒绝，而不是重新打开一个无人关闭的信箱。

## 模型体验

无：信箱是宿主侧的文件，本提供方写入的任何内容都不会被读回模型请求，随产品发布的组合中也没有挂载它。

#### KV Cache 影响

无；本包不贡献任何请求内容，因此不存在可被失效的前缀。

## 已知限制与暂缓事项

- **一个信箱一个写入方** —— 顺序与打开的句柄都是进程本地的。两个 harness 进程向同一路径追加可能交错写出半行；请给每个进程各自的信箱。
- **无上限增长** —— 没有任何机制轮转或截断该文件。长期运行的组合应把 `path` 指向由其自身清理机制负责的位置。
